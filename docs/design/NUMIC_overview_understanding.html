Neonatal cranial ultrasound · PHVD decision support

Understanding NUMIC

NUMIC turns the cranial ultrasound numbers a NICU team already records (ventricular size, how much it has changed since the last scan, and a short clinical-concern rating) into one explainable risk band: low, moderate or high. It supports the team's local pathway. It does not choose treatment.

Summary drawn from the repo's overview, stakeholder, evidence-premise, accelerator and demo docs, plus the code in src/numic and web/clinical-demo. Written 4 Oct 2026.

The clinical gap

In preterm infants, bleeding into the brain's ventricles (IVH) can lead to post‑haemorrhagic ventricular dilation (PHVD), which is linked to brain injury and poorer neurodevelopment. Management depends on three things: how dilated the ventricles are, how quickly they are getting bigger on serial cranial ultrasound (cUS), and how the baby is doing clinically.

Teams already measure three standard metrics on each scan:

VIVentricular index, compared against gestational-age percentile curves (97th‑centile line)
AHWAnterior horn width, in mm
TODThalamo‑occipital distance, in mm

The gap the docs identify: progression is often described loosely ("a bit bigger") and checked by hand against prior scans and cut‑offs. Nothing widely used combines absolute size, rate of change and clinical signs into one consistent, auditable summary for handover and governance. The anchor reference throughout is El‑Dib et al., J Pediatr 2020 (management of PHVD in preterm infants).

NumicFlow scoring

The score has three transparent layers that add up to a total out of 14. Every result records which versioned rule bundle produced it, so a result can be traced to an approved set of thresholds after the rules change.

Status & positioning

Product & business

  • Model: B2B SaaS, with an annual licence per NHS trust or neonatal network, optional pilot pricing in year one, and separate setup/integration fees.
  • Stage: pre‑revenue, bootstrapped, virtual company. The team is Eswari Mathialagan (software; Master's student at UCL), with clinical and other roles still TBC.
  • Funding path: an accelerator brief for Discovery Park / Discovery Spark (Kent), aimed at regulatory introductions and clinical advisers, plus an NIHR full-application template in the repo.
  • Assets: pitch deck (HTML), video pitch, accelerator brief, evidence-premise outline, and the website domain numic.uk on Carrd.

Regulatory & clinical posture (deliberately open)

  • Positioned as decision support, not diagnosis. Whether it counts as Software as a Medical Device, in which class, and whether it goes through UKCA or MDR is still to be settled with quality and clinical leads.
  • Planned governance topics: ISO 14971 risk management, IEC 62304 lifecycle, UK GDPR / DSPT, DPIA, human-factors testing, and clinical validation before any use near patients.
  • Evidence premise: serial cUS ventricular metrics form the backbone of escalation decisions. The docs avoid claiming causal outcome benefit until specific citations are in place.

Roadmap

Next steps: a proper clinician UI shaped with neonatologists and sonographers, persistence, deeper PACS/workflow integration, and later automatic VI/AHW/TOD from images, but only after clinical validation. Open user-research questions (the Harriet interview prep) cover NICU scanning cadence, how scans are compared across days, and which tools are already in use.

The clinical demo, as it works now

One screen. It takes patient context (demo ID, gestational age, VI reference), prior and current scans (date/time, VI, AHW, TOD, VI percentile), a 0/1/2 clinical modifier, and a rule-bundle selector with low, moderate and high presets. It shows the NumicFlow score, the highlighted band with suggested-action text, a live SVG trend chart (prior to current, with the VI reference line), and the raw JSON breakdown.

Browser ── GET /clinical-demo/* ──▶ FastAPI (uvicorn) ── StaticFiles(web/clinical-demo) │ │ ├─ GET /api/v1/score/versions ───────▶│ list_score_versions() └─ POST /api/v1/demo/numic-flow-from-record ▼ static + progression + clinical → total → risk_tier (same-origin; no auth, no CORS, nothing persisted)

What this means for hosting: the UI files are static, but scoring happens in Python on the server. The demo can't simply be dropped into a static site builder. Either a Python server runs somewhere, or the scoring moves into the browser.

Hosting it on numic.uk

Decision, 6 Oct 2026: option B on Railway. The demo will run as one FastAPI service with a PostgreSQL database on Railway at demo.numic.uk, linked from numic.uk. It uses the Levene rule set only, 10 synthetic babies and a private sandbox per visitor, with patient IDs generated automatically and no unit dashboard. The options below are kept for the record. Details: architecture, Demo deployment.

The website is on Carrd Pro Standard with a Namecheap domain. Carrd builds static, single-page sites. It can't run Python, and it can't serve a multi-file JS app as-is. Pro plans do allow embeds (including iframes) and custom domains. In every option, the demo lives on a subdomain such as demo.numic.uk (a CNAME at Namecheap), and the Carrd site either links to it or embeds it in an iframe.

Option A · my recommendation

Fully static demo

Port the ~60 lines of v1 scoring to JS (as this page does) and host web/clinical-demo on Cloudflare Pages, GitHub Pages or Netlify.

For

  • Free, no server to keep alive, instant load
  • No data leaves the visitor's browser, which helps the privacy story
  • Works offline and for investors on a slow link

Against

  • Rules exist twice (Python and JS). Fix: export bundles to one rules.json plus a parity test
Option B

Deploy the FastAPI app

Run the existing app (UI and API together) on Render, Fly.io, Railway or Cloud Run, mapped to demo.numic.uk.

For

  • One source of truth, and no code change to scoring
  • Shows a "real" backend and /docs

Against

  • Cost or free-tier cold starts (slow first load)
  • Visitor input reaches a server and its logs
  • Needs a requirements trim (asyncpg, pydicom and others aren't needed)
Option C

Hybrid

Static UI on Pages, with the API on a serverless function and CORS configured.

For

  • Fast UI, with the Python rules kept authoritative

Against

  • Most moving parts for a demo
  • Still sends inputs to a server

For a public marketing demo, A fits best: the scoring is simple, deterministic and already well specified. B suits a private demo for clinical partners who want to see the real system.

Things I noticed while reading

Read-only observations. Nothing has been changed.

Before public

The demo shows action text, while the brief says no treatment text is emitted. The API returns only a band, but the UI shows "Urgent escalation" and "Tighter surveillance". On a public page that reads like clinical advice. Consider neutral labels or "per your local pathway" wording, and keep the "not for patient care" banner prominent.

Before public

Free-text "clinical notes" and "patient ID" invite real data. On an open website, someone may type identifiable details. Remove those fields, or lock them to synthetic values, for the hosted version. Under option B this matters more, because input reaches server logs.

Clinical logic

Progression ignores the time between scans. Both scan dates are collected, but scoring uses only the mm difference. A 2 mm rise over 2 days scores the same as over 3 weeks, yet the docs frame the score as "how fast". This is worth raising with clinicians (mm/day, or interval-aware bands).

Clinical logic

The VI percentile and 97th-centile reference are typed in by hand. Gestational age is captured but not used. A nomogram lookup from GA and VI would remove a manual step and a source of error, which matches the brief's "less repetitive manual work" claim.

Housekeeping

The demo has uncommitted work. trend.js is untracked, and index.html, app.js and styles.css are modified. Hosting should start from a committed snapshot so the live site is reproducible.

Housekeeping

The docs overlap. NUMIC_overview.md, _for_stakeholders.md and the .docx are near-duplicates. questions.md stops mid-sentence ("only 8 % of"). The team table is mostly TBC.

Questions for our demo discussion

  1. Audience: is the website demo for investors and accelerators (public, polished, simplified) or for clinicians (closer to the real workflow)? The answer decides between A and B.
  2. Placement: should it be embedded inside the Carrd page (iframe section) or opened as its own page at demo.numic.uk? Full-page works much better on phones.
  3. Raw JSON: keep the JSON breakdown, or replace it with the readable per-layer bars shown above?
  4. Copy: what should the band labels and suggested-action wording say on a public page, given the "no treatment text" stance?
  5. Extras: should it include a short guided walkthrough (three presets with a sentence each) for people who don't know what VI, AHW and TOD are?
