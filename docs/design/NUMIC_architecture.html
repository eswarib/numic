Principles

Scoring is a plain library

The scoring engine has no web or database code. The API, the analytics job and the public demo all call the same logic, and it can be tested on its own.

Clinical rules are versioned data

Thresholds live in rule-set revisions, not in code or environment settings. A published revision never changes, and every result names the revision that produced it.

A person stays in charge

NUMIC suggests a band and explains it. Clinicians decide. Rule changes, including suggestions from data, need an approver.

Everything is explainable

Every result carries its layer points, the reference values used, the age at scan and any rule that raised the band.

Audit everything, log nothing personal

The audit trail records who did what to which record. Application logs never contain patient identifiers.

Two separate deployments

The public demo uses synthetic data, has no login, and keeps visitor entries in private sandboxes. The clinical system has sign-in, a governed database and approvals. They share the scoring engine and rule-set files.

Key flows

Score a new scan

  1. Clinician signs in IAM and opens the baby CLN · PAT.
  2. Enters scan date/time and VI, AHW, TOD MEA, plus clinical concern.
  3. API checks the role and unit, then loads date of birth and gestational age API · PAT.
  4. Rule engine supplies the active revision, e.g. numic_flow_levene@1 RUL.
  5. Scoring engine works out age at scan, reference lines, layer points, band and explanation SCR.
  6. Result and inputs are stored with the revision ID DAT, and the action is audited LOG.
  7. Clinician sees the band, reasons and trend chart CLN.

Record the clinician's decision

  1. Decision capture is switched on for the deployment CFG.
  2. Clinician records the final band, reasons and action CLN · DEC.
  3. NUMIC stores it against the result with decided-at and recorded-at times. Corrections replace, never edit DEC · DAT.
  4. Later, interventions such as lumbar puncture or shunt are recorded as outcomes DEC.
  5. Unit dashboard shows any results still waiting for a decision DSH.

Change a rule set

  1. Admin opens the published revision and clicks Edit, which creates a pre-filled draft ADM · RUL.
  2. Rule engine validates the draft and previews which recent results would change band RUL · SCR.
  3. A different person with the approver role approves with a reason ADM · IAM.
  4. The draft is published as a new revision and becomes active. Old results keep their revision RUL · DAT.
  5. Every step is in the audit trail LOG.

Learn from decisions and outcomes

  1. A scheduled job takes a pseudonymised extract LRN · DAT.
  2. Agreement dashboard compares predicted and clinician bands LRN · ADM.
  3. With enough cases, a regression proposes thresholds as a draft revision with evidence LRN · RUL.
  4. The draft follows the normal approval flow. Nothing is applied automatically ADM.

Deployments

Public

Demo at demo.numic.uk

  • One Railway service running FastAPI, which serves the demo pages and the API, plus a Railway PostgreSQL database.
  • Linked from the Carrd site on numic.uk; demo.numic.uk points to Railway.
  • Levene rule set only, 10 synthetic babies, and a private sandbox per visitor. No login.
  • Details in Demo deployment below.
Clinical

Hospital deployment

  • Front end, API and PostgreSQL hosted in the UK, signed in through the hospital's identity provider.
  • All components except DEMO. Decision capture and the learning loop are switched on per deployment.
  • Needs clinical safety (DCB0129/0160), DPIA and information-governance approval before real patient data.
  • One deployment per trust or network to start, so data stays with its owner. Shared hosting is an open decision.

Demo deployment

Decided on 6 Oct 2026. The demo uses the real Python backend so that visitors see the actual system, kept small enough to build and run cheaply.

Hosting

  1. Visitor clicks the demo link on numic.uk (Carrd).
  2. demo.numic.uk (CNAME at Namecheap) points to one Railway service running FastAPI.
  3. FastAPI serves the clinician app pages and /api/v1 from the same address, so no cross-site setup is needed.
  4. FastAPI reads and writes a Railway PostgreSQL database in the same project. PostgreSQL rather than MySQL, because the database models already use PostgreSQL-specific types (JSONB, UUID) and the asyncpg driver.

Data: seed babies and visitor sandboxes

  • 10 synthetic babies in one demo NICU, shared by everyone and read-only. Their dates are stored as offsets from today and rebuilt daily, so ages stay realistic. The set covers mostly low, some moderate and at least two high bands, plus one first-scan-only baby and one out-of-chart-range scan.
  • A private sandbox per visitor, created on the first visit and identified by a random token kept in the browser and sent in a request header. A header works even when the demo is embedded in another site, where browsers often block cookies.
  • Babies and scans carry a sandbox ID. Seed rows have none. Each visitor sees the seed rows plus their own, never anyone else's. A scan added to a seed baby changes that baby's chart only for that visitor.
  • Patient IDs are generated automatically (e.g. DEMO-7K3Q). There are no name or free-text fields.
  • Limits and clean-up (proposed): 20 babies and 30 scans per baby per sandbox, 60 writes a minute per IP address, and sandboxes deleted after 7 days without activity.

Before launch: the Levene 97th-centile values must be taken from Levene 1981 and checked by a clinician. Full requirements: Public demo.

Build order

Each phase is usable on its own and builds on the one before.

  1. Levene rule setLevene reference table, age at scan, explanation output, rule-set JSON file for numic_flow_levene.SCR · RUL (file only)
  2. Hosted demoRailway with FastAPI and PostgreSQL at demo.numic.uk: clinician app, 10 synthetic babies, visitor sandboxes, generated patient IDs.DEMO · CLN · API · PAT · MEA · DAT · CFG (demo slices)
  3. Brouwer rule setBrouwer tables and 2-point rules once decided, added to the demo and the core.SCR · RUL
  4. Foundations for real dataFull patients and units, sign-in and roles, audit trail, settings, security work.DAT · PAT · MEA · IAM · LOG · CFG · SEC
  5. Clinical screensClinician app for real use, unit dashboard, assessment report.CLN · DSH · RPT · API
  6. Governed rule changesAdmin console with rule editor, impact preview, approval and rollback.ADM · RUL
  7. Decisions, agreement and learningDecision and outcome capture, agreement dashboard, threshold suggestions, integrations.DEC · LRN · EXT

Open architecture decisions

  • Front-end approach: stay with plain ES modules or adopt a framework once there are three apps.
  • Hosting: the demo runs on Railway; the clinical deployment still needs UK or NHS-approved hosting and an operator.
  • Demo running cost: Railway plan, keeping the service awake, and database size.
  • One deployment per trust or shared hosting with strict separation between units.
  • Identity provider per pilot site, and whether NUMIC holds any role data itself.
  • Where rule-set revisions live: database only, or database plus exported JSON for the demo and audits.
  • Clinical decisions still open in the rule-set design: Brouwer 2-point thresholds, minimum-band rules, first-scan policy.
