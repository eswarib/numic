NUMIC requirements / Cross-cutting

Audit trail, logging & monitoring

Keep three separate records. The audit trail answers who entered, viewed, changed, approved or decided what and when, for clinical safety and governance. Application logs help engineers fix problems and must never contain patient identifiers. Monitoring shows whether the system is healthy and raises alerts when it is not.

Scope

In scope

  • Append-only audit table and the list of audited actions
  • Audit viewer and export in the admin console
  • Structured application logs with request IDs
  • Patient-identifier scrubbing and tests for it
  • Health checks, metrics and alerts
  • Retention periods for each record type

Out of scope

  • Clinical decisions themselves (owned by DEC)
  • Rule-set revision content (owned by RUL; changes to it are audited here)
  • Security incident response process (owned by SEC)

Users, data and interfaces

Users and callers

  • Clinical safety officer and governance staff (audit trail)
  • Admins and approvers (audit viewer)
  • Engineers and support (application logs, monitoring)
  • Trust information governance (access reviews)

Data it owns

  • Audit events: actor, role, action, entity type, entity ID, timestamp, before/after difference, reason, request ID, source IP
  • Application log stream (outside the clinical database)
  • Metrics and alert definitions

Interfaces

  • Internal audit.record(...) call used by every component that changes data
  • GET /api/v1/audit with filters (approver and admin only)
  • GET /api/v1/audit/export (CSV)
  • GET /health (exists) plus a readiness check that includes the database
  • Metrics endpoint for the hosting platform's monitoring

Functional requirements

IDPriorityRequirementAcceptance criterion
LOG-F01MustAudit events are stored in an append-only table. The application can insert rows but never update or delete them.The database role used by the app has INSERT and SELECT only on the audit table; an UPDATE attempt fails.
LOG-F02MustEach audit event records actor, role, action, entity type, entity ID, timestamp, before/after difference, reason (where given) and request ID.A rule-set edit produces one event showing the changed fields with old and new values.
LOG-F03MustAudited actions include sign-in, sign-out and failed sign-in; patient create and update; measurement create and correction; scoring runs; patient record views; decisions and outcomes; rule-set draft, edit, approve, publish, rollback and retire; user and role changes; exports.A test performs each action once and finds exactly one matching audit event.
LOG-F04MustViewing a patient's record is audited, not only changes to it.Opening the patient view in the clinician app writes a 'patient.viewed' event with the user and patient ID.
LOG-F05MustAdmins and approvers can search the audit trail by user, patient, action and date range in the admin console.Filtering by one patient and a date range returns only that patient's events in time order.
LOG-F06MustAudit search results can be exported to CSV, and the export itself is audited.Downloading an export creates an 'audit.exported' event with the filter used.
LOG-F07MustApplication logs are structured JSON lines with timestamp, level, request ID, route and duration.Each request produces a log line that parses as JSON and carries the same request ID returned in the X-Request-ID response header.
LOG-F08MustApplication logs never contain patient identifiers: names, MRN, date of birth, or free-text clinical notes.An automated test sends requests containing marker identifiers and fails if any marker appears in captured logs.
LOG-F09MustValidation errors in logs name the field and the problem but not the submitted value.A rejected spreadsheet row logs 'row 4: vi_mm out of range', not the patient ID or value.
LOG-F10MustHealth and readiness checks report whether the app and database are reachable.With the database stopped, the readiness check returns 503 while /health still returns 200.
LOG-F11MustMetrics cover request rate, error rate, latency and scoring runs, and alerts fire when the error rate or latency crosses a threshold (proposed: 5xx above 1% for 5 minutes).In a staging test, forcing errors triggers an alert to the configured channel.
LOG-F12ShouldAudit events are chained with a hash of the previous event so tampering can be detected.A verification command reports the first altered row after a row is edited directly in the database.
LOG-F13ShouldRetention periods are configurable per record type. Proposed: application logs 90 days; audit trail kept for the trust's health-records retention period.Logs older than the configured period are removed by the scheduled job; audit rows are not.
LOG-F14CouldApprovers see a weekly summary of rule-set changes and exports.The summary lists every publish, rollback and export from the past 7 days.
