NUMIC requirements / Deployments

Public demo

The public demo shows investors, accelerators and clinicians how NumicFlow turns serial cranial ultrasound measurements into an explained risk band, using the real Python backend. It runs on Railway as one FastAPI service with PostgreSQL at demo.numic.uk, linked from numic.uk, with synthetic data only. Every visitor starts with 10 pre-loaded synthetic babies and gets a private sandbox to add their own.

Scope

In scope

  • Railway hosting at demo.numic.uk: one FastAPI service plus PostgreSQL
  • Clinician app screens: baby list, baby view, add baby, add scan, trend chart, explained band
  • Rule engine limited to numic_flow_levene, loaded from its JSON file
  • Scoring engine: age at scan, Levene VI line, fixed AHW and TOD cut-offs, progression, clinical layer
  • 10 pre-loaded synthetic babies in one demo NICU
  • A private sandbox per visitor, with patient IDs generated automatically
  • Thin slices of patients, measurements, data layer, API and configuration

Out of scope

  • Unit dashboard
  • Brouwer rule set (added later)
  • Admin console, rule editing and approvals
  • Login and roles
  • Decision capture, outcomes and the learning loop
  • Reports and export
  • Real patient data and any free-text fields

Users, data and interfaces

Users and callers

  • Investors and accelerator reviewers
  • Clinicians evaluating the idea
  • Visitors to numic.uk

Data it owns

  • Seed file of 10 synthetic babies, with dates stored as offsets from today
  • Visitor sandboxes and the babies and scans added in them

Interfaces

  • numic.uk (Carrd) links to demo.numic.uk, or embeds it
  • FastAPI /api/v1 on the same origin as the pages
  • Sandbox token sent in the X-Demo-Sandbox header. A header is used instead of a cookie so the demo also works inside an embedded frame, where browsers often block cookies

Sandbox design

  • One table of sandboxes: random ID, created at, last seen at.
  • Babies and scans carry a sandbox ID. Seed rows have none and are shared and read-only. Rows added by a visitor carry that visitor's sandbox ID.
  • Every query shows seed rows plus the current sandbox's rows, never another sandbox's.
  • Scans added to a seed baby are stored with the visitor's sandbox ID, so the baby's chart changes only for that visitor.
  • Clean-up: a daily job deletes sandboxes inactive for 7 days (proposed) and rebuilds the seed dates relative to today.

DEMO-F01MustDeploy the demo as one Railway service running FastAPI, serving the demo pages and /api/v1 from the same address, with a Railway PostgreSQL database.demo.numic.uk serves the pages and the API over HTTPS from one origin; the browser makes no cross-site requests.
DEMO-F02MustPoint demo.numic.uk at Railway with a CNAME record at Namecheap, and link to it from the Carrd site at numic.uk.The demo button on numic.uk opens demo.numic.uk with a valid certificate.
DEMO-F03MustScore with numic_flow_levene only and hide the rule-set selector. Brouwer is added later.Every result names numic_flow_levene@1; /api/v1/score/versions lists only that rule set in the demo deployment.
DEMO-F04MustPre-load 10 synthetic babies into one shared demo NICU that no visitor can change.A new visitor sees 10 babies, each with at least two scans; attempts to edit or delete them return 403.
DEMO-F05MustStore the seed babies' dates as offsets from today (born N days ago, scanned on day k) and rebuild real dates on start-up and daily, so ages stay realistic on any date.On any date, every seed scan falls at a plausible age, and inside the Levene chart range except where a case is meant to show the out-of-range message.
DEMO-F06MustMake the seed set cover a useful spread: mostly low, some moderate, at least two high, one baby with only a first scan, and one scan outside the Levene chart range.A test scores the seed set and checks the band mix and the two special cases.
DEMO-F07MustCreate a private sandbox for each visitor on their first visit, identified by a random token kept in the browser and sent with every API request in an X-Demo-Sandbox header.Two browsers each see only their own additions; a request without a valid token gets a new sandbox, never another visitor's.
DEMO-F08MustLet visitors add babies and scans in their sandbox, including new scans for seed babies. Additions are visible only in that sandbox and never change the seed data.A scan added to seed baby DEMO-0003 in browser A changes its chart in A only; browser B and the stored seed rows are unchanged.
DEMO-F09MustGenerate each new baby's patient ID automatically (for example DEMO-7K3Q). Visitors cannot type or edit an ID, and there are no name fields.The add-baby form has no ID or name inputs; IDs are unique and shown read-only.
DEMO-F10MustCollect only date of birth (defaulting to a recent synthetic date), gestational age at birth (weeks + days), and for each scan the date and time, VI left and right, AHW, TOD and clinical concern. No free-text fields.The forms contain no free-text inputs; the API rejects unknown fields.
DEMO-F11MustShow the trend chart over age at scan with the Levene 97th-centile line and the line + 4 mm, and the explained band: layer points, plain-language reasons and the rule revision.For a baby with two or more scans, both lines, all points and the band for each scan appear; no raw JSON is shown.
DEMO-F12MustShow a disclaimer on every screen: synthetic data only, not for patient care, do not enter real patient details.The banner is visible on load at every screen width.
DEMO-F13MustUse neutral band wording with no treatment instructions.No band text tells the reader to take a specific clinical action.
DEMO-F14ShouldOffer a Reset my sandbox button that removes the visitor's additions.After reset the visitor sees only the 10 seed babies with their original scans.
DEMO-F15MustDelete sandboxes and their data after 7 days without activity (proposed) with a scheduled clean-up job.A sandbox last used 8 days ago no longer exists, and its babies and scans are gone from the database.

Non-functional requirements

IDPriorityRequirementAcceptance criterion
DEMO-N01MustLimit each sandbox to 20 babies and 30 scans per baby (proposed), and rate-limit writes to 60 per minute per IP address (proposed).Going over a limit returns 429 with a message saying which limit was reached.
DEMO-N02MustKeep the demo database separate from any clinical deployment and hold synthetic data only.The demo uses its own Railway project and database; no clinical credentials exist in it.
DEMO-N03MustSet no tracking cookies. The sandbox token is random and not linked to the visitor's identity, and application logs record only path, status and timing, not entered values.A log review after test traffic shows no measurement values, dates of birth or tokens.
DEMO-N04MustWork at phone width.No horizontal page scrolling at 400 px; forms and chart are usable on a phone.
DEMO-N05ShouldLoad quickly, with the Railway service kept running rather than sleeping.Proposed: interactive within 2 s on a mobile connection, including the first visit of the day.
DEMO-N06MustUse the same scoring code and the same numic_flow_levene rule-set file as the clinical system.The demo runs the shared scoring package; a test confirms the demo's rule-set file matches the published revision.

Open questions

  • Blocker: Levene 97th-centile values must be taken from Levene 1981 and checked by a clinician before launch.
  • Seed babies' scan histories to be reviewed by a clinician for realism.
  • Railway plan and monthly cost, including keeping the service running.
  • Link to a full page or embed in a Carrd section (a full page works better on phones).
  • Sandbox retention period (7 days proposed) and limits (20 babies, 30 scans proposed).
