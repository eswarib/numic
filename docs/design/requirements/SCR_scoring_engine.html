NUMIC requirements / Core logic

Scoring engine

The scoring engine turns one baby's scan inputs into a NumicFlow result using exactly one published rule-set revision. It works out age at scan, looks up reference lines, scores the static, progression and clinical layers, combines them into a band and explains how each part contributed. It is a pure Python library with no database or web code, so the API, the learning loop and the public demo can all run the same logic.

Scope

In scope

  • Age-at-scan calculation from date of birth, gestational age at birth and scan date
  • Reference-line lookup with linear interpolation
  • Static, progression and clinical layers
  • Combining layers: weights, band cut-offs, minimum-band rules, first-scan policy
  • Explanation output

Out of scope

  • Storing results (DAT, via API)
  • Choosing or editing rule sets (RUL)
  • Capturing or validating raw measurements (MEA)
  • Clinical decisions (DEC)

Users, data and interfaces

Users and callers

  • API layer (assessment and stateless scoring endpoints)
  • Rule engine (impact preview re-scoring)
  • Learning loop (re-scoring historical cases)
  • Public demo (browser port that must give identical results)

Data it owns

  • None persisted. Inputs and outputs are in-memory value objects.

Interfaces

  • score(case, revision) → ScoreResult (Python)
  • age_at_scan(dob, ga_weeks, ga_days, scan_at, tz) → weeks
  • reference_value(table, age_weeks) → mm
  • Shared JSON rule-set format read by the browser port (DEMO)

Functional requirements

IDPriorityRequirementAcceptance criterion
SCR-F01MustWork out age at scan as gestational age at birth plus (scan date in the scan-day time zone minus date of birth) divided by 7, with the day of birth as day 0.Born 2 Mar 2026 at 27+3, scanned 14 Mar 2026 09:00 Europe/London, gives 29.14 weeks (to 2 dp).
SCR-F02MustReject a case with no date of birth or gestational age when the revision uses any age-based metric, and reject a scan dated before the birth.Each case returns a validation error that names the missing or invalid field; no score is produced.
SCR-F03MustLook up a reference-line value by age using linear interpolation between whole-week table rows.At 29.5 weeks the value equals the mean of the 29 and 30 week rows; at exactly 30 weeks it equals the 30 week row.
SCR-F04MustRefuse to score a metric when age at scan is outside the reference table range, with an "outside chart range" result.Brouwer at 23.6 weeks returns outside chart range for VI, AHW and TOD and no band.
SCR-F05MustScore each static metric as either a fixed threshold or a reference line plus offsets, using the points per band defined in the revision.Levene: AHW 5.9 → 0, 6.0 → 1, 10.0 → 1, 10.1 → 2; TOD 24.9 → 0, 25.0 → 1, 29.9 → 1, 30.0 → 2; VI at the 97th line → 1, at line + 4 mm → 2.
SCR-F06MustApply the revision's VI side policy, defaulting to the larger of left and right.Left 11.0 mm and right 12.5 mm scores VI using 12.5 mm and the explanation names the side used.
SCR-F07MustScore progression from worsening in mm since the prior scan, treating shrinkage as 0, with cut-offs from the revision (default VI/AHW 1 and 2 mm, TOD 2 and 4 mm).VI +1.9 mm → 1, +2.0 mm → 2; TOD −3 mm → 0.
SCR-F08ShouldSupport a revision setting that scores progression in mm per day instead of mm, using the time between scans.With rate_basis mm_per_day, the same 2 mm rise over 2 days and over 21 days produce different points.
SCR-F09MustScore the clinical layer from none, mild or clear concern using the revision's points (default 0, 1, 2).Clear concern adds 2 points with the default revision.
SCR-F10MustCombine layers using the revision's layer weights and band cut-offs (default low ≤ 3, moderate ≤ 7).Default weights: total 3 → low, 4 → moderate, 8 → high.
SCR-F11MustApply the revision's minimum-band rules after the sum and report every rule that raised the band.With rule any_metric_2pt → moderate enabled, static 0/0/2 with total 2 returns moderate and names the rule.
SCR-F12MustApply the revision's first-scan policy when there is no prior scan.A case without a prior is scored according to the configured policy and the explanation states that no trend was available.
SCR-F13MustReturn an explanation with age at scan, reference value and distance from the line per metric, points per layer, progression deltas, the rule revision ID and any minimum-band rules applied.Every result contains these fields; the revision ID is the exact family@n used.
SCR-F14ShouldScore a batch of cases against one revision in a single call.500 stored cases re-score in one call and return one result per case in input order.

Non-functional requirements

IDPriorityRequirementAcceptance criterion
SCR-N01MustKeep the library pure: no database, HTTP or file I/O imports.An automated test fails if any module under scoring/ imports sqlalchemy, fastapi, httpx or opens files.
SCR-N02MustProduce identical output for identical inputs and revision.Re-running the full test corpus twice gives byte-identical results.
SCR-N03MustCover every threshold boundary with tests for both rule sets.Tests exist for the value just below, at and above every cut-off in numic_flow_levene and numic_flow_brouwer.
SCR-N04ShouldScore one case quickly enough for interactive use (proposed under 10 ms).Benchmark of 1,000 cases averages under 10 ms per case on the reference server.
SCR-N05MustMatch the browser port used by the public demo exactly.A shared test corpus produces the same points and band in Python and JavaScript.
