NUMIC requirements / Extensions

Learning loop & analytics

Use real cases to check how well NUMIC's bands match what clinicians decide and what happens to the baby, and to suggest better thresholds over time. It starts with a simple agreement dashboard that is useful from the first cases. Later, once there is enough data, an offline job fits a model and proposes a draft rule-set revision. Nothing it produces is ever applied without the normal review and approval.

Scope

In scope

  • Agreement dashboard
  • Pseudonymised analysis extract
  • Outcome-based analysis
  • Threshold suggestion job
  • Evidence report for each suggestion
  • Versioned data and model snapshots

Out of scope

  • Publishing rule-set revisions (RUL and ADM)
  • Recording decisions and outcomes (DEC)
  • Any real-time scoring change

Users, data and interfaces

Users and callers

  • Approvers and clinical leads
  • Admins
  • Clinical researchers and data analysts
  • Clinical safety officer

Data it owns

  • Pseudonymised analysis extracts (dated snapshots)
  • Fitted model snapshots and their settings
  • Threshold suggestions with evidence (threshold_suggestions table)

Interfaces

  • GET /api/v1/analytics/agreement with revision, unit and date filters
  • GET /api/v1/analytics/suggestions and /{id}
  • Scheduled job command, e.g. numic-suggest-thresholds
  • Draft revision created through the rule engine's normal draft interface

Functional requirements

IDPriorityRequirementAcceptance criterion
LRN-F01MustShow a 3 × 3 agreement table of NUMIC's predicted band against the clinician's band, filtered by rule revision, unit and date range.With 10 seeded synthetic cases, the table counts match a hand calculation.
LRN-F02MustShow the override rate overall and per predicted band, plus weighted kappa as a single agreement figure.Weighted kappa on a seeded dataset matches the value from a reference statistics library.
LRN-F03MustShow which metrics were abnormal in overridden cases, so admins can see what drives disagreement.For seeded overrides with large TOD only, the dashboard lists TOD as the most common abnormal metric.
LRN-F04MustProduce a pseudonymised extract for analysis: no names, MRN or date of birth. Age at scan replaces date of birth, and patients get a random study ID.A scan of the extract finds no direct identifiers; the same patient keeps the same study ID within one extract.
LRN-F05MustThe extract keeps the raw inputs (mm values, changes, time between scans, age at scan, clinical concern), the layer scores, the rule revision, the predicted band, the clinician band and outcomes.Every column needed by the suggestion job is present and documented.
LRN-F06ShouldAnalyse outcomes by band, e.g. time from each band to lumbar puncture, reservoir or shunt.The report shows outcome counts and time-to-event per predicted band.
LRN-F07ShouldA threshold suggestion job fits an ordinal logistic regression on the raw inputs and turns the fitted model into suggested cut-offs.Run on synthetic data generated from known thresholds, the job recovers those thresholds within a set tolerance.
LRN-F08ShouldEach suggestion is checked with cross-validation and reports agreement before and after, calibration, case count and the cases that would change band.The evidence report contains each of these sections.
LRN-F09MustA suggestion is saved as a draft rule-set revision and is never published automatically.After the job runs, the active revision is unchanged and a new draft exists with author 'learning loop'.
LRN-F10MustThe job only runs once a configurable minimum number of cases exists (NUMIC_MIN_CASES_FOR_SUGGESTION). Below that it reports 'not enough data yet'.With fewer cases than the setting, the job exits without creating a draft.
LRN-F11MustThe job runs offline on a schedule or on demand, never inside a user request.Scoring latency is unchanged while the job is running.
LRN-F12MustEach run stores a versioned snapshot of the input extract and the fitted model so results can be reproduced.Re-running from a stored snapshot gives the same suggested cut-offs.
LRN-F13MustThe dashboard and reports state the limits: the clinician band is not ground truth, clinicians may be anchored by seeing NUMIC's band first, and small event counts make estimates unstable (rule of thumb: 10 to 20 events per model parameter).These caveats appear on the suggestion review screen.
LRN-F14LaterSupport a blinded evaluation mode where the clinician records their own band before seeing NUMIC's.In blinded mode, the decision is saved before the band is shown, and both are linked.

Non-functional requirements

IDPriorityRequirementAcceptance criterion
LRN-N01MustNo analysis runs on real patient data until the governance route is approved: research ethics, HRA or CAG approval, or an agreed service evaluation.Approval reference recorded in the job configuration before a real-data run.
LRN-N02MustAnalytics access uses a separate read-only database role limited to the pseudonymised extract.The analytics role cannot read the patient table.
LRN-N03ShouldThe agreement dashboard loads in under 3 seconds for one unit's year of data (proposed).Measured on seeded data.
LRN-N04ShouldUpdating thresholds from data follows a predetermined change control plan agreed with regulatory advisers.Plan document exists before the first suggestion is published.
