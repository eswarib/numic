NUMIC requirements / Data

Data layer

The data layer stores everything NUMIC needs to keep: units, patients, scans and measurements, scored results with their explanation, rule-set revisions, decisions, outcomes and the audit trail. It uses PostgreSQL with Alembic migrations so the schema can change safely once real data exists.

Code DATLayer Data Partly exists SQLAlchemy async models for PostgreSQL exist in src/numic/db/ (Patient, ImagingStudy, MeasurementRun, Measurement, ProgressionEvaluation, ClinicalAssessment, RiskReport). No migrations; the demo does not use the database. 9 functional · 4 non-functional · 10 must

Scope

In scope

  • Schema and migrations
  • Integrity and constraints
  • Backups and restore
  • Retention
  • Pseudonymised analytics extract

Out of scope

  • Business rules (SCR, RUL)
  • Access control decisions (IAM)

Users, data and interfaces

Users and callers

  • All core components through repository code
  • Learning loop through a pseudonymised extract

Data it owns

  • All persistent tables: units, patients, unit stays, imaging studies, measurements, progression evaluations, risk reports, rule-set revisions, reference tables, decisions, outcomes, users/roles, audit entries, threshold suggestions

Interfaces

  • SQLAlchemy async session
  • Alembic migrations
  • Pseudonymised extract for LRN

Functional requirements

IDPriorityRequirementAcceptance criterion
DAT-F01MustUse PostgreSQL with Alembic migrations for every schema change.A fresh database reaches the latest schema with alembic upgrade head, and each migration has a downgrade.
DAT-F02MustAdd date of birth and gestational age at birth to Patient, and add a NICU unit table.Migration adds the columns and unit table; existing rows remain valid.
DAT-F03MustReplace the vi_percentile and vi_p97_reference_mm columns with the reference values used.No percentile or reference input columns remain; results store reference values from scoring.
DAT-F04MustStore every result with its inputs snapshot, explanation and rule revision ID.Each RiskReport row references a revision and holds the explanation JSON.
DAT-F05MustAdd tables for rule-set revisions, reference tables, decisions, outcomes, audit entries, users/roles and threshold suggestions.Tables exist with foreign keys to the records they describe.
DAT-F06MustEnforce referential integrity and prevent deletion of clinical records by the application user.The app database user has no DELETE permission on clinical tables.
DAT-F07MustBack up daily with point-in-time recovery (proposed) and test restores.A restore test is run and recorded at least every quarter (proposed).
DAT-F08MustApply a configurable retention policy that follows the trust's records policy.Records past retention are identified and handled by a documented procedure.
DAT-F09ShouldProvide a pseudonymised extract for analytics with no names, MRN or date of birth.The extract uses age at scan and a study ID; a test confirms no identifiers are present.

Non-functional requirements

IDPriorityRequirementAcceptance criterion
DAT-N01MustEncrypt data at rest and host in the UK.Hosting configuration shows encrypted storage in a UK region.
DAT-N02ShouldMeet proposed recovery targets: data loss under 24 hours, service back within 4 hours.A recovery drill meets both targets.
DAT-N03MustKeep score_version and revision IDs within 32 characters.Column length is 32 and longer IDs are rejected by the rule engine.
DAT-N04ShouldKeep typical queries fast (proposed: unit dashboard query under 200 ms for 100 active babies).Load test meets the target.
