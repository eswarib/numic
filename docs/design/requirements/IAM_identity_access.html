NUMIC requirements / Cross-cutting

Identity & access

Make sure only the right people can see and change NUMIC data, and that every action is tied to a named person. Staff sign in with their existing hospital account rather than a NUMIC password. Roles decide what a user can do, and unit scoping decides which babies they can see.

Code IAMLayer Cross-cutting Not built No login or roles exist today. Every endpoint in src/numic/api/v1 is open, and src/numic/core/config.py has no auth settings. 14 functional · 4 non-functional · 15 must

Scope

In scope

  • Sign-in through the hospital identity provider (OIDC)
  • Roles: viewer, clinician, admin, approver
  • Unit scoping of patient data
  • Session lifetime and idle timeout
  • Service accounts with scoped tokens
  • Role and unit assignment for users
  • Audit events for sign-in, sign-out and failures

Out of scope

  • Managing staff passwords or MFA (the identity provider does this)
  • Public demo, which has no login
  • Hospital directory management

Users, data and interfaces

Users and callers

  • Clinicians (neonatologists, sonographers, nurses)
  • Rule-set admins
  • Approvers (e.g. unit clinical lead)
  • Read-only viewers (e.g. audit, governance)
  • Integration services (service accounts)
  • Trust IT / identity team

Data it owns

  • User record: identity-provider subject ID, display name, email, active flag
  • Role assignments per user
  • Unit assignments per user
  • Service accounts and their scopes (token hashes only)

Interfaces

  • OIDC authorisation-code flow with PKCE against the trust identity provider
  • GET /api/v1/auth/me: current user, roles, units
  • POST /api/v1/auth/logout
  • Admin endpoints to assign roles and units (via ADM)
  • Bearer-token check applied to every /api/v1 route except /health

Functional requirements

Must needed for a first clinical pilot Should expected soon after Could useful if time allows Later future phase
IDPriorityRequirementAcceptance criterion
IAM-F01MustUsers sign in through the hospital identity provider using OIDC (e.g. NHS or Microsoft Entra ID). NUMIC stores no passwords.A user with a valid trust account reaches the clinician app after the identity-provider login; the NUMIC database has no password column.
IAM-F02MustLocal username and password accounts exist only for development and test, and are switched off in clinical deployments.With the clinical deployment profile, local login returns 404 and startup logs that local accounts are disabled.
IAM-F03MustFour roles exist: viewer, clinician, admin and approver. A user can hold more than one.Each role's allowed actions are listed in a permission table and covered by tests that call every protected endpoint with every role.
IAM-F04MustViewers can read patients, results and dashboards for their units but cannot change anything.A viewer's POST, PUT or DELETE on any clinical endpoint returns 403.
IAM-F05MustClinicians can enter scans, run scoring, view results and record decisions and outcomes for their units.A clinician can create a measurement and a decision for a patient in their unit; the same calls for another unit return 403.
IAM-F06MustAdmins can create and edit draft rule-set revisions, manage unit settings and assign roles. Only approvers can publish a revision.An admin's publish request returns 403; an approver's publish request on a valid draft returns 200.
IAM-F07MustAn approver cannot approve a draft they created or last edited.Publishing a draft whose author is the approver returns 403 with a message saying a different approver is needed.
IAM-F08MustEvery user is scoped to one or more NICU units and can only see patients in those units.Listing patients returns only babies from the user's units; fetching a patient from another unit returns 404.
IAM-F09MustEvery /api/v1 call needs a valid token, except /health. The public demo is a separate deployment with no login.An automated test calls every registered route without a token and expects 401, apart from /health.
IAM-F10MustSessions end after a configurable idle time, so shared ward computers do not stay signed in. Proposed default: 15 minutes.After the configured idle period, the next request is rejected and the app returns to sign-in.
IAM-F11MustSign-in, sign-out, failed sign-in and token refusal are written to the audit trail.Each event appears in the audit table with user (or attempted subject), time, source IP and outcome.
IAM-F12MustIntegrations use service accounts with tokens limited to named scopes (e.g. measurements:write) and an expiry date.A service token with measurements:write cannot read patient lists; an expired token returns 401.
IAM-F13ShouldAdmins can disable a user immediately in NUMIC, independent of the identity provider.A disabled user's next request returns 403 even with a valid identity-provider token.
IAM-F14ShouldMulti-factor authentication is enforced through the identity provider's own policy.Trust IT confirms MFA is required for the NUMIC application registration.

Non-functional requirements

IDPriorityRequirementAcceptance criterion
IAM-N01MustTokens are verified against the identity provider's published keys, with issuer, audience and expiry checked.Tokens with a wrong issuer, wrong audience, bad signature or past expiry are each rejected in tests.
IAM-N02MustRole and unit checks run in the backend for every request. Hiding buttons in the UI is never the only protection.Calling a protected API directly with an under-privileged token returns 403.
IAM-N03MustSession cookies are Secure, HttpOnly and SameSite=Lax or stricter. Tokens never appear in URLs or logs.Security test of the deployed app shows the cookie flags; a log scan finds no token strings.
IAM-N04ShouldPermission checks add less than 20 ms to a request (proposed).p95 overhead measured under load test stays below the target.

Open questions

  • Which identity provider each pilot trust uses, and whether NUMIC is registered per trust or once nationally.
  • Whether role assignment is managed in NUMIC or through identity-provider groups.
  • Idle timeout value agreed with the unit (15 minutes is a proposal).
  • Whether clinicians from a neighbouring unit need temporary access during transfers.
