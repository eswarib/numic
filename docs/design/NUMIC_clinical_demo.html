NUMIC clinical demo

The public demo of NumicFlow at demo.numic.uk: what it does, how it is built, every setting it reads, and how to run it on Railway with PostgreSQL. It implements the Public demo requirements (DEMO v2) on the branch pr/clinicaldemo.

Describes the code at commit e553b5b on pr/clinicaldemo. Start-up against PostgreSQL 16 was checked locally on 7 Oct 2026; the demo is not deployed yet.

What visitors can do

  • See the baby list: 10 shared, read-only seed babies (DEMO-0001 to DEMO-0010) plus any they added.
  • Open a baby: trend charts of VI, AHW and TOD over age at scan, with the Levene 97th-centile line and the line + 4 mm for VI, and the fixed AHW and TOD cut-offs. Every scan shows its band, layer points, plain-language reasons and the rule revision numic_flow_levene@1.
  • Add a baby: date of birth (synthetic, defaults to a week ago) and gestational age at birth in weeks and days. The patient ID (for example DEMO-7K3Q) is generated. There are no name, ID or free-text fields.
  • Add a scan to any baby, including seed babies: date and time, VI left and right (the larger is scored), AHW, TOD and clinical concern. A scan added to a seed baby is visible only to that visitor.
  • Delete babies or scans they added, or reset their sandbox to remove everything they added.

Day of life and age at scan are worked out, never typed: age at scan = gestational age at birth + (scan date in Europe/London − date of birth) ÷ 7, with the day of birth as day 0.

Levene values are provisional. The Levene 97th-centile table in src/numic/rule_sets/tables/levene_vi_p97.json has "verified": false, and the demo shows a note saying so. The values must be replaced with ones read from Levene 1981 and checked by a clinician before launch.

Sandboxes

  • The browser keeps a random token in localStorage and sends it in the X-Demo-Sandbox header. A header rather than a cookie keeps the demo working inside an embedded frame, where browsers often block cookies.
  • A request without a valid token gets a new sandbox, and the token comes back in the X-Demo-Sandbox response header. A visitor is never given another visitor's sandbox.
  • Seed rows have sandbox_id = NULL; rows a visitor adds carry their sandbox ID. Every query returns seed rows plus the current sandbox's rows. Deleting a seed baby or seed scan returns 403.
  • last_seen_at is refreshed at most every 5 minutes, which keeps database writes low.

Seed babies

  • Stored as "born N days ago, scanned on day k at HH:MM" and re-dated on start-up and whenever the day changes, so ages stay realistic on any date. Visitor scans on seed babies move with them.
  • The spread is 6 low, 2 moderate and 2 high. DEMO-0004 has only a first scan. DEMO-0009's first scan (24+5 weeks) is outside the Levene chart and shows "Not scored" instead of a guessed line. tests/test_demo_sandbox.py checks this.
  • These bands were set against the provisional Levene values. They may shift once the real values are loaded, and the seed should be re-checked then.

Demo API

All demo endpoints take the X-Demo-Sandbox request header. Requests that change data count towards the write limit.

MethodPathWhat it doesWrite limit
GET/api/v1/demo/babiesSeed babies plus the visitor's, with each baby's latest bandNo
POST/api/v1/demo/babiesAdd a baby (date of birth, gestational age weeks and days); returns 201 with the generated IDYes
GET/api/v1/demo/babies/{baby_id}One baby with all visible scans, each scored, and the chart dataNo
DELETE/api/v1/demo/babies/{baby_id}Delete a baby the visitor added; 403 for seed babiesYes
POST/api/v1/demo/babies/{baby_id}/scansAdd a scan; returns 201Yes
DELETE/api/v1/demo/babies/{baby_id}/scans/{scan_id}Delete a scan the visitor added; 403 for seed scansYes
POST/api/v1/demo/sandbox/resetRemove everything the visitor added; returns 204Yes
GET/healthHealth check used by RailwayNo

Errors: 404 for a baby or scan not visible to the visitor; 403 for changing seed data; 422 for invalid input: a date of birth in the future or more than a year ago, gestational age outside 22+0 to 42+6 weeks, a scan before the birth or in the future, VI, AHW or TOD outside 0–40 mm (TOD 0–60 mm), or any unknown field; 429 when a limit is reached, with a message naming the limit; 503 if the database is unavailable.

The stateless scoring endpoints (/api/v1/score/...) and the older /api/v1/demo/numic-flow-from-record are also served. The full schema is at /docs.

PostgreSQL

Database service

  • Add Railway's PostgreSQL database to the demo project. It runs in the same project as the app, so the app reaches it over Railway's private network.
  • Railway gives the database two connection strings. DATABASE_URL uses the private network and is the one the app should use. DATABASE_PUBLIC_URL goes through a public proxy and is only for connecting from your own computer.
  • In the app service, set DATABASE_URL=${{Postgres.DATABASE_URL}}. This is a reference variable, so it follows the database if its credentials change. Use the database service's actual name if it isn't called Postgres.
  • The driver is asyncpg. The app converts Railway's postgresql:// URL to postgresql+asyncpg://, so the URL needs no editing.

Tables

Created automatically on start-up with SQLAlchemy create_all. There are no migrations, because the demo only holds synthetic data.

TableColumnsNotes
demo_sandboxesid (token, PK), created_at, last_seen_at (indexed)One row per visitor.
demo_babiesid (patient ID, PK), sandbox_id (FK, cascade, NULL for seed), date_of_birth, ga_weeks, ga_days, seed_born_days_ago, created_at10 seed rows plus visitor rows.
demo_scansid (PK), baby_id (FK, cascade), sandbox_id (FK, cascade, NULL for seed), measured_at, vi_left_mm, vi_right_mm, ahw_mm, tod_mm, clinical_concern, created_at24 seed rows plus visitor rows.

Deleting a sandbox deletes its babies and scans through the foreign-key cascades. The database stays tiny: each sandbox is capped at 20 babies with 30 scans each.

Lifecycle

  • Start-up: create any missing tables, load or re-date the seed babies for today, delete expired sandboxes, then start the hourly job.
  • Every hour: delete sandboxes unused for 7 days, and re-date the seed if the day has changed in Europe/London.
  • Backups: not needed for synthetic data. Losing the database only loses visitors' sandboxes; the seed is rebuilt on start-up.

Changing the tables later

create_all only creates missing tables; it never changes existing ones. If a later change edits src/numic/demo/models.py, drop the three demo tables and restart the service so they are recreated. Visitors' sandboxes are lost, which is acceptable for synthetic data. The clinical system will need real migrations (Alembic).
DROP TABLE IF EXISTS demo_scans, demo_babies, demo_sandboxes;

Railway

railway.json at the repository root holds the service settings, so they are versioned with the code:

{
  "$schema": "https://railway.com/railway.schema.json",
  "build": { "builder": "NIXPACKS" },
  "deploy": {
    "startCommand": "uvicorn numic.main:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips '*'",
    "healthcheckPath": "/health",
    "healthcheckTimeout": 60,
    "restartPolicyType": "ON_FAILURE",
    "numReplicas": 1,
    "sleepApplication": false
  }
}
SettingWhy
builder: NIXPACKSDetects pyproject.toml and installs the package. The rule-set and seed JSON files are inside the package (checked: the built wheel contains all three), and the pages are found from the working directory, so a normal install works.
startCommandRuns uvicorn on Railway's $PORT. --proxy-headers makes the app see the client address forwarded by Railway's proxy. Use a single uvicorn process (no --workers).
healthcheckPath: /healthRailway waits for a 200 from /health before switching traffic to a new deployment. The tables and seed are ready by then, because start-up does them first.
restartPolicyType: ON_FAILURERestarts the service if it crashes.
numReplicas: 1Required. The write-rate limiter and the maintenance job run inside the process, so a second replica would double the limits and run the job twice.
sleepApplication: falseKeeps the service running so the first visitor of the day doesn't wait for a cold start (DEMO-N05).

Railway's newer builder, Railpack, could replace Nixpacks later. Check Railway's current plans and prices before choosing one; an always-on service and a small database are needed.

Deploy step by step

  1. Create a separate Railway project for the demo

    Keep it apart from anything clinical (DEMO-N02). Name it, for example, numic-demo.

  2. Add PostgreSQL

    In the project, add a PostgreSQL database. Keep the default service name Postgres, or note the name you choose.

  3. Add the app service from GitHub

    Create a service from the eswarib/numic repository. Set the deploy branch to pr/clinicaldemo for now, and to main once the pull request is merged.

  4. Set the variables on the app service 
    DATABASE_URL=${{Postgres.DATABASE_URL}}
NIXPACKS_PYTHON_VERSION=3.12

    Leave every NUMIC_* setting at its default unless you want different limits.

  5. Deploy

    Railway builds with Nixpacks and starts the command from railway.json. In the deploy logs, check that the build installed the package and that uvicorn reports it is running.

  6. Try the Railway address

    Open the generated *.up.railway.app address. It should redirect to /clinical-demo/ and show the 10 seed babies.

  7. Add the custom domain

    In the app service's networking settings, add demo.numic.uk. Railway shows a CNAME target.

  8. Add the DNS record at Namecheap

    In Advanced DNS for numic.uk, add a CNAME record with host demo and the target Railway showed. Railway issues the HTTPS certificate once DNS resolves.

  9. Link from numic.uk

    On the Carrd site, point the demo button at https://demo.numic.uk/. A link to the full page works better on phones than an embedded frame.

Run it locally

python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
uvicorn numic.main:app --reload --host 127.0.0.1 --port 8000

Open http://127.0.0.1:8000/. With no database configured, the demo uses a local SQLite file, numic-demo.db. Other useful addresses: /health and /docs. Run the tests with pytest.

Known limitations

  • One process only. The write limiter and the maintenance job live in memory, so the service must run as one replica with one uvicorn worker.
  • The write limit is best-effort. It counts per client IP taken from X-Forwarded-For, which a client can influence. It stops casual misuse, not a determined attacker.
  • No migrations. Changing the demo tables means dropping them (see PostgreSQL).
  • Provisional Levene values. Bands and seed spreads may change when the real values are loaded.
  • Brouwer is not included yet. It needs its tables and 2-point rules first.
  • The older demo endpoint /api/v1/demo/numic-flow-from-record is still served; the new UI doesn't use it.

Before launch

  • Blocker: replace the provisional Levene 97th-centile values with values read from Levene 1981, have a clinician check them, and set "verified": true. The provisional-values note then disappears.
  • Clinician review of the seed babies' scan histories, and a re-check of the band spread with the real values.
  • Confirm sandbox retention (7 days) and the limits (20 babies, 30 scans, 60 changes a minute).
  • Choose the Railway plan, and decide whether to link from numic.uk or embed.
  • Merge pr/clinicaldemo into main, then switch the Railway deploy branch to main.
